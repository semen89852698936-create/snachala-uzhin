# «СНАЧАЛА УЖИН»: архитектура продаж, российского хостинга и бессрочного доступа

Статус: **предпроектная техническая схема (не включены оплаты, рассылка, логин или продакшен-перенос)**.
Дата: 2026-11-03. Все изменения должны проходить тесты и быть совместимы с текущим проектом. Условия продажи: единоразово **1900 ₽**, без подписки, доступ бессрочный (пока не отозван по обоснованному возврату).

## Принятые исходные требования

- Целевая аудитория и платежи: РФ, оплата российскими картами и доступными методами, сайт без VPN.
- Бренд самостоятельный, без имени Семёна Чайки.
- Каталог 1001 рецепт; интерактивные шаги, списки покупок, «Наш вечер» сохраняются как веб-продукт, не заменяются PDF.
- Покупатель не вводит сложный пароль, не зависит от исходного браузера и не пересылает чеки вручную.
- Не надо менять утверждённые изображения «Наш вечер» или публиковать новый лендинг без проверки.
- Не смешивать покупательские данные другого продукта и этого продукта.

## Рекомендованная инфраструктура

1. **Timeweb Cloud App Platform** в явно выбранном регионе РФ: сайт + backend через Dockerfile и GitHub. Технический домен с HTTPS для тестов, затем собственный домен .ru (имя и доступность проверить отдельно). Альтернатива до миграции: оставить Vercel только как некоммерческую тестовую среду.
2. **PostgreSQL с хранением в РФ, вне ephemeral Docker-контейнера**. Данные: email пользователя, заказ, уникальный ID платежа, права доступа, кодовые токены/сессии в хэшированном виде, аудит выдач и возвратов. Бэкап и план восстановления. Приложение Timeweb App Platform при повторном деплое пересоздаёт контейнер: нельзя хранить покупки только в SQLite-файле контейнера.
3. **Prodamus** для оплаты. Режим самозанятого с автоматической интеграцией «Мой налог», если рабочая платёжная страница и права уже активированы. До запуска сверить договор, комиссию, условия самозанятости, чек, уникальный merchant endpoint, актуальную документацию HMAC. Не копировать/публиковать секреты в GitHub.
4. **Транзакционная почта** с собственным доменом и настроенными SPF/DKIM/DMARC: отправлять код входа и подтверждение заказа. Выбор провайдера и его договор/размещение данных утверждаются после теста доставки на Яндекс Почту, Mail.ru, Gmail.
5. **Закрытое хранилище каталога**: отдельное приватное хранилище данных/закрытый репозиторий с рецептами либо защищённая таблица. Рецепты запрашиваются через backend после проверки прав. Публичный репозиторий и открытые страницы должны содержать только демонстрационные данные.

## Обнаруженная проблема в текущем проекте

- Полный каталог встроен напрямую в публичные `index.html` и `full-catalog/index.html`.
- Текущий `server.py` использует `SimpleHTTPRequestHandler` и отдаёт файлы без проверки авторизации.
- Поскольку репозиторий публичный, просто закрыть HTML интерфейсом или CSS нельзя; исторически опубликованные исходники нельзя гарантированно отозвать у тех, кто их уже получил.
- Для будущего платного выпуска нужно перенести содержимое закрытой части на серверную сторону, а доступ к файлам строго ограничить. Сохранение репозитория в приватном состоянии само по себе недостаточно, если сервер всё равно раздаёт полный каталог.
- Запрет индексации в `robots.txt` не является механизмом авторизации.

## Сценарий покупки и выдачи

1. Посетитель открывает лендинг, видит демонстрационные рецепты и нажимает «Получить доступ за 1900 ₽».
2. Backend создаёт заказ `order_id` с серверной фиксированной ценой 1900 RUB, `product_id=snachala-uzhin-lifetime`, email, статусом `pending`; клиент не может подменить цену или `order_id`.
3. Backend создаёт подписанную платёжную ссылку/параметры Prodamus, выполняет переход на платёжную форму провайдера. Карточные реквизиты не проходят через наш сервер.
4. После оплаты Prodamus отправляет server-to-server webhook на `POST /api/payments/prodamus/webhook`. Backend проверяет HMAC по документации Prodamus, статус успешной оплаты, ID заказа, сумму, валюту и уникальность идентификатора операции. При недостоверной подписи или несоответствии полей права не выдаются. Повторы webhook безопасны (идемпотентно).
5. Backend транзакционно помечает заказ `paid`, создаёт `lifetime` право на доступ для этого email; отправляет письмо для входа. Redirect пользователя после оплаты НЕ считается доказательством платежа.
6. Страница после оплаты показывает «Проверяем оплату…», проверяет статус заказа по непривилегированному токену заказа. После подтверждения предлагает вход. При задержке webhook пользователь может открыть письмо и вернуться позже.
7. Вход: email -> одноразовый код (например, действителен 10 минут, с ограничением числа попыток и скорости запросов) -> HttpOnly Secure SameSite session cookie. Возможны несколько устройств, но подозрительные входы мониторятся; пароль не обязателен.
8. При новом устройстве пользователь снова подтверждает email. Отозвать доступ по обоснованному возврату можно контролируемо, сохраняя историю транзакций.
9. При сбоях выдачи после успешной оплаты сохранять оплаченный заказ, повторно обрабатывать уведомление, иметь ручное восстановление через администратора. Никогда не отправлять покупателю секреты в открытом письме.

## Минимальные серверные маршруты

- `POST /api/orders` - новый заказ, серверная цена.
- `POST /api/payments/prodamus/webhook` - прием проверенного уведомления об оплате.
- `GET /api/orders/{id}/status` - без утечки чужих личных данных, только с секретным непривилегированным токеном статуса.
- `POST /api/auth/request-code`, `POST /api/auth/verify-code`, `POST /api/auth/logout` - вход и выход.
- `GET /api/me/entitlements` - доступные продукты.
- `GET /api/recipes`, `GET /api/recipes/{id}` - закрытые рецепты после проверки права.
- `GET /healthz` - проверка состояния, без секретов/персональных данных.

## Зона публичного доступа

- Утверждённый продающий лендинг в рамках отдельного PR #39 после актуализации условий.
- Демонстрационные рецепты: ограниченный набор, точное число определить редакционно (предлагается 10-20); интерфейс «Наш вечер» с демоданными.
- Страницы «Как работает», «Условия покупки и доступа», «Оферта», «Политика конфиденциальности», контакт для поддержки, восстановление доступа и возвраты.
- Не менять существующий публичный сайт до появления тестируемой защищённой версии и плана переключения DNS.

## Безопасность и законность

- Применить требования 152-ФЗ: данные российских покупателей и их хранение/обработка должны проходить с соблюдением требований локализации РФ; проверить подрядчиков (email, аналитика, базы).
- Проверить правовое основание обработки, статус оператора, уведомление Роскомнадзора при необходимости, тексты оферты/политики, требования к цифровому продукту и возвратам.
- Для самозанятого проверить интеграцию Prodamus с «Мой налог» и отсутствие двойного отражения дохода через банк (официальная инструкция Prodamus предупреждает о дублях).
- Ни при каких обстоятельствах не добавлять HMAC секрет, почтовый пароль, токены или реальные email покупателей в репозиторий, скриншоты, логи или тесты.
- Бэкапы PostgreSQL, мониторинг webhook, фиксирование успешной оплаты и ошибок выдачи.
- Закрытие от массовой выгрузки на уровне маршрутов и прав, rate limits. Пределы невозможности препятствовать скриншотам/копированию честно учитывать.

## Тестовые сценарии ДО приема реальных денег

- Демо без логина: только разрешённые рецепты; `/full-catalog/index.html` не выдаёт платное содержимое, старые публичные JSON/JS не раскрывают каталог.
- Неверный HMAC, неверная сумма, повторный webhook, возврат, отклонённая/прерванная оплата -> доступа нет либо состояние корректно обновляется.
- Успешная тестовая оплата -> запись заказа, право `lifetime`, письмо, вход с двух устройств, доступ к 1001 рецептам и интерактивным функциям.
- Сбой email после оплаты -> ручное восстановление без повторной оплаты; новый деплой -> сохранение данных покупателя.
- Мобильный браузер, Россия без VPN, медленный интернет, доступность локальных фото, отказ аналитики/Spotify не ломает рецепты.
- Проверить доставку и читаемость чека, статус в «Мой налог», корректность оформления цены 1900 ₽, обработку возвратов.
- Пройти smoke-тест на временном домене Timeweb, затем перенести DNS только после одобрения рабочей инфраструктуры.

## Конкретные стоп-факторы на 3 ноября 2026

1. Нет подтверждённого подключённого рабочего Prodamus merchant ID/платёжной формы именно для этого продукта; неизвестно, можно ли безопасно переиспользовать действующий кабинет другого проекта.
2. Нет проверенного российского production-хостинга, домена и постоянно действующей базы покупателей.
3. В текущей публичной версии присутствуют все 1001 рецепта и исходники проекта.
4. Нет серверной авторизации и защищённой выдачи, нет приёмки тестовых вебхуков.
5. Вопрос юридических документов, заключения оферты и фискализации нужно проверить перед включением коммерческих платежей.

**Не включать кнопку реальной оплаты до прохождения этих контрольных точек.** Разработка и тесты не требуют включать продажу.
