# Безопасное разделение каталога рецептов и интерфейса

## Фактическое устройство
- В `index.html` содержится 1001 рецепт. Это встроенный каталог, а не отдельный сервер PostgreSQL.
- Реестры фотографий находятся в `photo-library/`; состояние публикации и редакционное одобрение - разные вещи.
- Демонстрационный `server.py` возвращает на `/api/status` жёстко записанное `published_recipes: 21`. Этот счётчик устарел относительно полного каталога, и по нему нельзя судить о 1001 рецепте.
- Основной production Vercel и Git-связанный Vercel - отдельные проекты. Нельзя приравнивать успешный Git-просмотр к выпуску на основной сайт.

## Целевое состояние
1. `data/recipes.json`: 1001 реальная запись с неизменными ID, названиями, ингредиентами, шагами и категориями.
2. `data/recipes.schema.json`: структура полей и допустимые значения.
3. `data/recipe-assets.json`: явная связь по recipe_id, WebP-файл, контрольная сумма, источник, автор, лицензия и редакционный статус.
4. Автоматическая проверка: 1001 уникальный ID, существование каждого изображения, отсутствие неразрешённых дублей и битых ссылок.
5. Раздельные версии и резервные копии, Git PR, preview-тесты, выпуск только после разрешения.

## Последовательность миграции
1. Зафиксировать SHA действующей версии `index.html`, сделать резервную копию и исследовать формат встроенных записей.
2. В отдельной ветке извлечь все реальные рецепты *без редактирования содержания*. Проверить число и уникальность ID.
3. Создать JSON Schema и проверить данные. Сопоставить фото по ID, не по порядковому номеру.
4. Сохранить старую страницу как fallback и сделать тестовую версию, читающую внешний JSON.
5. Протестировать мобильный и настольный режимы, поиск, шаги, покупки, таймеры, роли и «Наш вечер».
6. Проверить соответствие опубликованных изображений конкретным рецептам и правила атрибуции.
7. После тестов и отдельного разрешения выпустить с возможностью отката.

## Когда подключать SQL
Пока сайт отдаёт общий каталог для чтения, JSON с проверками проще и дешевле полноценной БД. PostgreSQL понадобится при появлении учётных записей, постоянных пользовательских списков, заказов и прав доступа между устройствами. Тогда вводить миграции, серверное API и резервное копирование. Не хранить секреты БД во фронтенде.
