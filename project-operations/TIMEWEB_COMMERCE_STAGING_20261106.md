# Timeweb Cloud: отдельный коммерческий стенд «СНАЧАЛА УЖИН»

**Статус:** подготовка к развёртыванию, не публичный запуск продаж. **Не заменять действующий Vercel.**
Код этого стенда находится только в ветке `deploy/commerce-timeweb-staging-20261106`, производной от коммерческого PR #89 с проверенной защитой уведомлений Продамус из PR #128.


## Тарифная конфигурация, проверена 07.11.2026

**Бюджет пользователя:** не более 2 000 ₽/месяц для всего продукта на Timeweb, финальная стоимость до заказа согласуется отдельно. Создание платных ресурсов **ещё не разрешено**, развертывание не начато.

Проверка выполнена read-only GitHub Actions `.github/workflows/timeweb-tariff-quote.yml` через настоящий API Timeweb Cloud:
- `GET /api/v1/presets/apps` -> 200, московская зона `ru-3` (MSK-1).
- Минимальный backend preset `id=2731`: **510 ₽/мес**, **1 CPU, 1024 MiB RAM, 15360 MiB SSD/NVMe** (около 15 ГБ).
- Резервный backend preset `id=2733`: **810 ₽/мес**, **1 CPU, 2048 MiB RAM, 30720 MiB** (около 30 ГБ). Повышать только после измерений RAM.
- `GET /api/v2/presets/dbs` -> **403**, потому что у токена намеренно отсутствует доступ к «Базы данных». **НЕ считать оценку PostgreSQL подтверждённым тарифом личного кабинета**.
- План PostgreSQL: отдельная **managed** PostgreSQL в Москве, одна база и один пользователь, TLS и автоматическое резервное копирование. Рабочая смета пока **до 790 ₽/мес** (без публичного IP, если доступна приватная связь); точную стоимость в кабинете показать перед заказом. PostgreSQL не должна жить в контейнере App Platform.
- Почта ориентировочно **120 ₽/мес**, бэкапы ориентировочно **30–100 ₽/мес**, прочий резерв не менее **400 ₽/мес**.
- Оценка 510 + 790 + 120 + 100 = **1520 ₽/мес**, не финальный счёт. Не принимать допуслуги, выводящие итог свыше 2 000 ₽.
- Без подтверждённых тарифов БД и почты, согласования расхода и способа работы с секретами не выполнять `POST /api/v1/apps`, создание БД или запись аккаунтных ресурсов.

Базовый проект Timeweb `3145267`, название «СНАЧАЛА УЖИН». API secret `TIMEWEB_API_TOKEN` имеет управление **только App Platform**, прочие ресурсы закрыты. Проект «Мои границы» не затрагивать. Создание новых ресурсов через токен ограничено не только тарифом, но и отсутствием доступных секретов `SESSION_KEY_HEX`, `COMMERCE_BASE_URL`, `COMMERCE_DATABASE_URL`, SMTP и merchant. Подлинные секреты создавать и хранить лишь в хранилище платформы.

**Граница безопасности:** предварительная проверка `GET /api/v1/apps` вернула 200 и не показала приложения других проектов, но по этому одному ответу нельзя гарантировать отсутствие любых административных API-прав токена; при оплате и публикации нужны независимые проверки безопасности.


## Создание приложения в кабинете владельца Timeweb Cloud

1. Открыть Timeweb Cloud → **App Platform** → **Создать приложение**.
2. Источник: **GitHub** → репозиторий `semen89852698936-create/snachala-uzhin`; ветка **`deploy/commerce-timeweb-staging-20261106`**.
3. Фреймворк: **Dockerfile**; контекст сборки: корень репозитория, Dockerfile: **`Dockerfile`**. Это копия проверенного `Dockerfile.commerce`, а НЕ прежний статический сервер.
4. Регион: **Россия**. Для первого стенда выбрать недорогую конфигурацию после просмотра тарифов, без создания платных ресурсов без согласия владельца. Автодеплой по новым коммитам **выключить** до завершения проверок.
5. Health check: `/healthz`, приложение слушает порт **8080**. Платформа выдаст HTTPS-технический адрес. Настроить его как `COMMERCE_BASE_URL`; если при создании нужен первоначальный адрес, обновить переменную сразу после выдачи технического домена и повторно запустить деплой.
6. Переменные ниже задаются **только в личной панели Timeweb**. Никогда не копировать в GitHub или чат реальные пароли, ключи, токены:
   - `COMMERCE_BASE_URL=https://<выданный-технический-домен>`
   - `COMMERCE_DB_PATH=/srv/data/orders.sqlite` **только для временного стенда без покупателей**; состояние теряется при повторном развёртывании.
   - `SESSION_KEY_HEX` = случайный 64-символьный hex, созданный локально `openssl rand -hex 32` и внесённый в секретные переменные хостинга
   - `PRIVATE_CATALOG_HTML=/srv/private/app.html` (уже задано в Dockerfile)
   - `ENABLE_CHECKOUT=0`
   - `COMMERCE_PAYMENT_QA_APPROVED=0`
   - `PRODAMUS_URL=https://snachala-uzhin.payform.ru/` можно оставить как справочный URL, но **не включать оплату**
   - `PRODAMUS_SYS`, `PRODAMUS_SECRET`, `SMTP_PASSWORD` пока не вводить без официального подтверждения конфигурации
7. Для просмотра результата открыть **технический HTTPS-домен**. Проверить: `/healthz` → 200, `/account` → 200, `/app` → 403 без покупки, `/full-catalog/index.html` → 403, `/assets/recipes-ai/<реальный-файл>.webp` → 403, POST `/api/orders` с валидным Origin → 503. Никаких настоящих платежей не выполнять.

## Обязательные проверки перед реальным запуском продаж

- Развернуть **внешнюю управляемую PostgreSQL в российском регионе**; указать `COMMERCE_DATABASE_URL` в закрытых переменных, включить TLS, резервное копирование и **проверить восстановление**. Не держать платных покупателей на SQLite в контейнере.
- Настроить личный почтовый SMTP-отправитель с рабочей доставкой magic link. Доступ по email должен восстанавливаться на другом устройстве.
- Получить актуальные `PRODAMUS_SYS` и `PRODAMUS_SECRET` в кабинете провайдера; проверить подпись **реального** уведомления, сумму 1900 ₽, идентификаторы заказов, повторные уведомления, возврат, отмену и отсутствие выдачи доступа неоплатившим пользователям. Личная ссылка с `order_num`, а не общий URL товара.
- Проверить юридические тексты, самозанятость/чеки, обработку персональных данных в РФ, оферту, возвраты и защиту от перебора на внешнем прокси.
- Провести реальную сквозную проверку ПК/телефон/Россия без VPN, затем отдельным релизом перевести домен и только после проверки активировать `ENABLE_CHECKOUT=1` и `COMMERCE_PAYMENT_QA_APPROVED=1`.
- Код CI не должен оставлять образ с закрытым каталогом в открытом Docker Registry. GitHub Actions проверяет образ временно и **не публикует** его.
