# Личные кабинеты покупателей - технический контракт

Дата: 2026-11-10. Статус: **реализация авторизации и синхронизации ещё не завершена**.

## Требования
- После подтверждённой оплаты Продамус у покупателя появляется персональная учётная запись с бессрочным правом доступа к оплаченному продукту (1900 ₽ на старте). Покупка и аккаунт должны быть связаны сервером, а не клиентским флагом.
- Вход по email: одноразовая ссылка или одноразовый код, без хранения паролей в статическом HTML. Подтверждать принадлежность email до связывания покупки. Нужны ограничение частоты запросов и срок жизни кодов.
- Авторизованный пользователь видит свои любимые блюда, заметки и, после согласования хранения, список покупок на телефоне и компьютере.
- При первом входе импортировать существующие `su_favorites` и `su_recipeNotes` из localStorage, только после успешной авторизации, с сохранением имеющихся данных на сервере (merge), без потери заметок и без повторного импорта.
- На общем компьютере выход должен завершать сессию; избранное и заметки другого аккаунта не должны отображаться. Между пользователями данные строго изолированы.
- Не менять утверждённый журнальный дизайн и рецептурную базу. Текст о будущем появлении кабинета удалить из обоих HTML.
- Не открывать платные рецепты по одной лишь клиентской проверке: защита контента должна быть на сервере. Важно проверить и `full-catalog/index.html`, и статические JSON/HTML, чтобы не оставить публичный обход.
- Продамус: принимать уведомление через серверный webhook, проверять подпись по действующей документации провайдера, сверять сумму, валюту, идентификатор заказа и результат оплаты; обеспечить идемпотентность, не доверять success redirect из браузера.
- Открывать продажи только после реальной end-to-end проверки платежа, выдачи доступа, восстановления входа, отсутствия обхода каталога и доступности в РФ.

## Предлагаемые серверные таблицы
- `users`: id, verified_email (unique), created_at.
- `login_tokens`: user_id/email, digest токена, expiry, consumed_at, request metadata.
- `sessions`: user_id, digest сессионного токена, expiry, revoked_at.
- `orders`: order_id unique, user_id, amount, currency, payment_status, provider_txn_id unique.
- `entitlements`: user_id, product_code, valid_from, revoked_at (для бессрочного права дата окончания NULL).
- `user_recipe_data`: user_id, recipe_id, is_favorite, note, updated_at; PRIMARY KEY(user_id,recipe_id).
- Контроль доступа для каждой операции чтения/записи по server-side session user_id; ни один клиентский user_id не должен давать доступ к чужим данным.

## Приёмочные проверки
1. Гость может просмотреть только бесплатную часть; прямые ссылки на платные данные закрыты.
2. Подтверждённый покупатель получает кабинет и сохраняет доступ после закрытия браузера/входа на другом устройстве.
3. Избранное и заметки синхронизируются, переживают выход и повторный вход.
4. Старые локальные данные импортируются один раз; конфликт не стирает уже сохранённое.
5. Два покупателя не видят чужих данных; выход завершает сессию, CSRF/XSS и лимиты входа проверены.
6. Ошибочный/повторный webhook не выдаёт дополнительного доступа и не создаёт дублей.
7. На desktop/mobile оформление и функции каталога, аэрогриля, поиска и режима готовки сохранены.

## Текущий прогресс
В ветке `feature/customer-accounts-foundation-20261110` удалён устаревший текст `du-my-sync-note` в обоих HTML. **Это не означает, что кабинеты, платежи и облачная синхронизация уже работают.** Вливать и публиковать вместе с реализацией и проверками, а не как самостоятельный запуск кабинета.
