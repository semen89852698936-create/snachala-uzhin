# Продамус: техническая приёмка перед подключением

Дата: 2026-11-05. Статус: **проектирование, НЕ подключено**.

## Подтверждено владельцем в интерфейсе

- Канал «Сначала Ужин» активен; продукт «СНАЧАЛА УЖИН - бессрочный доступ к 1001 рецепту», 1900 ₽.
- Покупатель указывает обязательный email.
- Настройки канала → Уведомления → API уведомления → «Уведомления о разовых оплатах»: поле URL и события «Все события» / «Заказ оплачен». Интерфейс может связывать обе галочки.
- Настройки канала → Интеграции → генерация секретного API-ключа; **ключ не создан и не передан разработке**.

## Архитектурные ограничения и этапы

1. Пока не публиковать CTA оплаты и не вводить фиктивную выдачу доступа. Не указывать URL несуществующего обработчика.
2. Уточнить официальный формат callback, подпись, заголовки, код успешного ответа и повторы в актуальной документации Продамуса. API-ключ для исходящих запросов может отличаться от секрета подписи уведомлений; не смешивать их без документального подтверждения.
3. Создать серверный HTTPS endpoint; принимать только допустимый метод и размер запроса, валидировать подпись на исходном теле согласно спецификации, а не по неподписанному полю email/status.
4. Сопоставлять внешний заказ с собственной записью ожидаемой покупки: идентификатор, сумма 190000 копеек, валюта RUB, продукт, состояние. Никаких прав по одному редиректу браузера.
5. Идемпотентно сохранять события и выдавать entitlement в постоянном серверном хранилище с уникальным ключом заказа. Повторы и события не об успешной оплате не меняют доступ.
6. Отдельная авторизация покупателя по подтверждённой электронной почте (одноразовая ссылка/код с ограниченным сроком). Email из callback сам по себе не является доказательством владения почтой.
7. Закрыть серверной авторизацией не только UI, но и исходные HTML/JSON/JS с полным каталогом и медиа, если они содержат платный контент. Публичный статический каталог не становится защищённым от скрытия кнопок.
8. Тесты: поддельная/неверная подпись, неверная сумма, неверный продукт, неизвестный заказ, дублирование, события в неправильном порядке, повторная доставка, временная ошибка хранилища, проверка без авторизации, desktop/mobile.
9. Только после тестового подтверждения с разрешённым тестовым режимом настроить реальный webhook URL в кабинете, сохранить, сверить поступление и затем отдельно открыть продажи.

## Безопасность

Не помещать ключи, подписи, персональные данные покупателей и реальные платежи в GitHub, скриншоты или сообщения. Секреты хранятся только в защищённых переменных среды. Не менять платёжные настройки без отдельного подтверждения владельца.
